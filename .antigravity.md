# Streamcache VOD Proxy - System & Operating Requirements

This document defines the core operating requirements, constraints, and architectural designs for the **Streamcache** VOD caching proxy. All development agents working on this repository must read, respect, and keep this file up to date.

---

## 1. Project Overview
* **Goal**: A lightweight proxy server that caches Video-on-Demand (VOD) media streams on-demand from an upstream IPTV provider. It serves files directly from local disk when fully cached, and shares active downloads among multiple client players to prevent redundant bandwidth consumption.
* **Core Route Compatibility**:
  * Legacy base64 route: `/u/<base64_encoded_url>`
  * Query string route: `/stream?url=<url>`
* **Stack**: Go (native implementation with platform-specific system call optimization for Linux/Docker).

---

## 2. Core Operating Requirements & Design Decisions

### A. Strict Single-Upstream-Connection Limit
* **Requirement**: Enforce a maximum of **1 active upstream HTTP connection per media file** to protect the user's IPTV account from concurrent connection bans.
* **Implementation**: Spawns a single `UpstreamCoordinator` goroutine per VOD file to manage the sole active HTTP socket. Multiple concurrent clients reading the same file share this coordinator and read from the same local growing file on disk.

### B. Block-Based Sparse Caching
* **Requirement**: Support instant, lag-free seeking within files that have not finished downloading.
* **Implementation**: Files are divided into equal-sized blocks (default **2MB**). When a download starts, the proxy queries the CDN and pre-allocates the file space on disk using `Truncate`. Blocks are written concurrently/out-of-order directly to their offsets using thread-safe `os.File.WriteAt`.
* **Gaps & Gird**: Companion JSON files (`<filename>.json`) track the sparse block grid (`NotStarted`, `Downloading`, `Completed`). Gaps (skipped blocks) are back-filled sequentially when clients are satisfied.

### C. Debounced Fair Scheduler (Thrashing Prevention)
* **Requirement**: Allow different client players to stream different uncached ranges of the *same* file (e.g. Player A at 50%, Player B at 0%) using the single connection slot, without causing connection thrashing.
* **Implementation**: The coordinator time-slices the single connection between starving client block requests. It enforces a debounce limit:
  * **`SCHEDULER_MIN_BYTES`** (default `4MB`) must be downloaded, or
  * **`SCHEDULER_MIN_TIME`** (default `2s`) must have elapsed
  Before the connection is aborted and re-established at the other starving client's range. Handshake latency is hidden behind the players' playback buffers.

### D. Context-Aware Interruptible Reads
* **Requirement**: Immediately halt disk reads and clean up resources when players cancel/disconnect (e.g., Emby's `ffprobe` -> `ffmpeg` transition behavior), preventing memory or thread leaks.
* **Implementation**: Replaces standard polling loops with Go channel selects. Client readers wait on a `select` statement between block write signals and the HTTP request's `context.Done()`. If the context is cancelled, the reader unregisters itself from the starvation queue and exits instantly.

### E. Decoupled Coordinator Lifecycle
* **Requirement**: Upstream downloads must run to completion in the background even if the initial player connects and immediately disconnects (e.g., `ffprobe` scans headers and drops).
* **Implementation**: The `UpstreamCoordinator` runs in a separate background thread. If all clients disconnect, it continues downloading the file to EOF in the background to hydrate the cache.

### F. Cache Change Revalidation & Eviction
* **Requirement**: Detect if the IPTV provider modifies or replaces a VOD file on the CDN (for quality upgrades or index fixes), evict the old cache, and download the new stream.
* **Implementation**:
  * **Revalidation Probe**: On play, if the cache validation timestamp is older than `CACHE_REVALIDATE_INTERVAL` (default `1 hour`), the proxy makes a quick `GET bytes=0-0` request upstream.
  * **Change Detection**: Compares ETag, Last-Modified, and Content-Range total size. On mismatch, the cached video and metadata JSON are evicted (deleted) to trigger a fresh download. Soft-fails (keeps cache) if the CDN is offline.
  * **Pre-Eviction**: Keeps an O(1) running total of the cache size. As soon as hydration starts and the incoming media file size is determined, pre-evicts inactive completed files in LRU order if adding the incoming file would exceed `CACHE_MAX_BYTES` or drop physical disk free space below `MIN_DISK_FREE_BYTES`.

### G. Asynchronous Pipelined Writeback, LiveBuffer & Non-Blocking Commits (`SyncFileRange` + `Fadvise`)
* **Requirement**: Prevent slow storage or disk commits from blocking upstream network ingestion or freezing concurrent hydrations, and prevent Docker containers from exhausting cgroup memory limits due to dirty page accumulation.
* **Implementation**:
  * **Writeback Ring Buffer**: Workers stream incoming chunks into a bounded producer-consumer queue (`WRITEBACK_BUFFER_SIZE`, default `64MB`). A dedicated storage consumer goroutine writes chunks to disk without blocking network ingress.
  * **LiveBuffer Fast-Path**: Recent chunks are retained in a sliding in-memory window (`LiveBuffer`). Active players streaming near the live download edge read directly from RAM (sub-0.1ms TTFB), bypassing disk I/O entirely.
  * **Native Linux Writeback Pacing**: The storage consumer paces writebacks on Linux using `unix.SyncFileRange(SYNC_FILE_RANGE_WRITE)` in 8MB windows, followed by `unix.SyncFileRange(WAIT_BEFORE|WRITE|WAIT_AFTER)` and `unix.Fadvise(POSIX_FADV_DONTNEED)` once pages are clean on physical storage. This prevents page cache accumulation and eliminates `balance_dirty_pages()` unkillable D-state blocking on other hydrations. (Stubs to no-op on Windows/Darwin).
  * **Decoupled Commit Handoff**: When download reaches 100%, the coordinator detaches the file and hands finalization off to a background goroutine (`finalizeAndCommitCache`), immediately returning so the coordinator never blocks. The UI reflects `Committing 100.0%` until the background rename is complete.
  * **S3 Chunking Synergy**: The 64MB bounded writeback queue aligns 1:1 with the planned S3 64MB chunking pipeline ([S3_STORAGE_BACKEND_PLAN.md](file:///home/adrien/opencode_projects/SC2/S3_STORAGE_BACKEND_PLAN.md)).

### H. Client Signature Emulation & Redirects
* **Requirement**: Emulate media player signatures to bypass Cloudflare/CDN blocks.
* **Implementation**: Clones and forwards client headers (`User-Agent`, `Cookie`, etc.) upstream. Falls back to a generic VLC player footprint (`VLC/3.0.18 LibVLC/3.0.18`) for background downloads. Uses a custom `CheckRedirect` policy to force header/cookie propagation across multi-hop redirects.

### I. Diagnostics & Debugging Suite
* **Requirement**: Expose runtime statuses for AI agents or remote debuggers.
* **Implementation**:
  * `/debug/state`: Exposes in-memory registry status, block grids, and scheduler queue JSON.
  * `/debug/pprof/`: Full Go runtime thread/CPU/heap profiling.
  * `/debug/logs`: SSE endpoint for streaming live application logs.

## 3. Future & Planned Architectural Extensions

### A. S3-Compatible Tiered Storage Backend (OVHcloud, AWS, MinIO)
* **Status**: Speculative Design / Planned Roadmap.
* **Specification Document**: See [S3_STORAGE_BACKEND_PLAN.md](file:///home/adrien/opencode_projects/SC2/S3_STORAGE_BACKEND_PLAN.md).
* **Summary**: Enables progressive 64MB chunked uploads to an S3-compatible backend (such as OVH Object Storage) during hydration, capping local scratch disk usage to 2–4 GB for 60+ GB 4K VOD files. Lagging or concurrent viewers stream committed S3 chunks directly (zero local disk usage), and completed chunks are recomposed server-side via `UploadPartCopy` into a final monolithic object with zero proxy bandwidth.
